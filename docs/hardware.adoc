== Hardware

=== Target microcontroller

Tuna targets the *Microchip AVR64DD14*, a member of the AVR-DD family:

[cols="1,3",options="header"]
|===
| Property | Value

| Core            | 8-bit AVR, mainline avr-gcc supported
| Flash           | 64 KB
| Package         | 14-pin
| System clock    | 24 MHz, internal high-frequency oscillator with auto-tuning
| `F_CPU`         | `24000000UL` — must stay in sync with the clock configuration
|===

The clock is configured in `hal_init()` (`src/hal.c`) by writing
`CLKCTRL.OSCHFCTRLA` to select the 24 MHz internal oscillator with auto-tune
enabled. `F_CPU` is defined to match (defaulted in `hal.c`, and also passed by
the build via `-DF_CPU=24000000UL`). **If you change the clock, change both.**

[WARNING]
====
`F_CPU` feeds two time-critical calculations:

* the sample-rate timer top value
  (`COUNTER_TOP_VALUE = F_CPU / SAMPLE_FREQ - 1`), and
* the `<util/delay.h>` busy-wait delays used by the startup splash.

A mismatch between the real clock and `F_CPU` silently changes the sample rate
(and therefore every reported frequency) and the delay timing.
====

=== Signal acquisition path

[cols="1,3",options="header"]
|===
| Peripheral | Role

| `ADC0`
| 12-bit single-ended conversion. Reference is `VDD` (5 V). The ADC clock is set
  to `CLK_PER / 16` = 1.5 MHz (the device maximum at 24 MHz) via
  `ADC_PRESC_DIV16_gc`; without this the default prescaler runs the ADC far above
  its specified maximum and yields inaccurate conversions. `SAMPCTRL` is extended
  to 14 to settle higher source impedances.

| `TCA0`
| Free-running timer that paces conversions. `PER` is set to
  `COUNTER_TOP_VALUE` so it overflows at exactly `SAMPLE_FREQ`.

| `EVSYS`
| Event system. The TCA0 overflow is routed on channel 0
  (`EVSYS_CHANNEL0_TCA0_OVF_LUNF_gc`) directly to the ADC start trigger
  (`USERADC0START`, `ADC_STARTEI_bm`). Each conversion is started *in hardware*
  at the timer overflow, eliminating the ISR-latency jitter that software-started
  conversions would suffer.

| `ADC0_RESRDY` ISR
| Fires when a conversion completes. It reads `ADC0.RES`, subtracts
  `ADC_ZERO_OFFSET` (= `1 << 11` = 2048) to re-centre the VDD/2-biased,
  AC-coupled input to a signed range of −2048..+2047, and hands the sample to the
  acquisition callback.
|===

The analog front end is *AC-coupled and biased at VDD/2*, so a quiet input sits
near mid-scale. The fixed `ADC_ZERO_OFFSET` removes the nominal bias; any small
residual DC is further removed downstream (the FFT path subtracts the per-frame
mean before windowing, and silence detection measures deviation from the frame
mean rather than absolute magnitude).

The input is sampled on `ADC0.MUXPOS = ADC_MUXPOS_AIN4_gc` (analog input AIN4).

=== Display path

The display is a *MAX7219* LED driver chip, driving:

* two 7-segment digits (note letter + octave), and
* a 20-element LED bar graph (the tuning needle).

The MAX7219 is *bit-banged* over three GPIOs on PORT C:

[cols="1,1,2",options="header"]
|===
| Signal | Pin | Direction

| `DIN`  | PC1 | output (serial data in)
| `CLK`  | PC2 | output (shift clock)
| `LOAD` | PC3 | output (latch / `CS`)
|===

[NOTE]
====
*Why bit-bang instead of hardware SPI/USART?* The manufactured board wires the
shift clock to *PC2*. On the AVR64DD14 there is no SPI0/USART pin-mux option that
can output a hardware shift clock on PC2 while simultaneously driving serial data
on PC1. A hardware serial peripheral therefore cannot drive this display layout,
so the three lines are toggled in software in `max7219_write()`.
====

=== Display register map

The firmware uses the MAX7219's five digit registers (digit 0..4):

[cols="1,2,3",options="header"]
|===
| MAX7219 digit | `display.c` index | Purpose

| `DIGIT_0` | 0 | 7-segment: note letter (with decimal point for accidentals)
| `DIGIT_1` | 1 | 7-segment: octave number
| `DIGIT_2` | 2 | bar graph segments (packed)
| `DIGIT_3` | 3 | bar graph segments (packed)
| `DIGIT_4` | 4 | bar graph segments (packed)
|===

At init the driver sets scan limit to 4 (digits 0–4), intensity to maximum
(`0x07`), and takes the chip out of shutdown. `max7219_reset()` zeroes all 16
registers first, which also defines the known-zero starting state that the
display shadow framebuffer relies on.
